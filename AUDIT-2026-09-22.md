# WebTorrent Desktop audit — 22 September 2026

**Assessment: usable for basic playback, but not ready for a trusted release. Fix the network exposure and renderer permission boundary first.**

Audited the current local `modernization/electron-43-webtorrent-3` worktree, based on commit `a347573`, including the uncommitted paste, privacy, and tracker changes, and `/Applications/WebTorrent.app` on Apple Silicon. The installed app and latest packaged `app.asar` have the same SHA-256: `0c3fc878a4256470d211c3fe7a51a33a5adcdeeef5ed2f43a88d3247c564966d`.

This was an audit, not a remediation pass. No application source, dependency versions, installed bundle, or normal user settings were changed during the audit. Tests used a separate profile and harmless temporary fixtures. Process execution and trash actions were intercepted when testing authorization bypasses; no real commands were launched or files trashed by those probes.

**Prioritized findings**

1. **High — The media HTTP server exposes active torrents without authentication. Reproduced in the installed app.**

   `ensureServer()` creates the server with default options and calls `listen(0)` without a bind address. The actual listener was `::`, not loopback. A request with an arbitrary Host and Origin received HTTP 200, `Access-Control-Allow-Origin: *`, a torrent listing, and the audit file contents. Calling the app's `stopServer` left it listening. The source comment claiming it “only serves localhost” is incorrect. Poster generation can also start this shared server, so exposure is not confined to deliberate casting.

   Impact: reachable machines can enumerate/read active torrent content when host firewall/network rules permit. Browser abuse additionally depends on browser local-network protections; it was not tested from a remote website. No second physical LAN machine was used.

   Fix: bind local playback to loopback; authenticate and limit any separately enabled LAN casting service; disable public listing and unrestricted cross-origin access; restrict Host; serve only authorized files and stop/restrict service when no longer needed.

   Sources: [webtorrent.js:351](src/renderer/webtorrent.js#L351), [webtorrent.js:385](src/renderer/webtorrent.js#L385), `node_modules/webtorrent/lib/server.js`.

2. **High — Renderer-controlled saved state defeats the claimed main-process authorization boundary. Reproduced with stubbed privileged effects.**

   `stateSave` accepts essentially any object, then the main process replaces its supposedly authoritative state with it. The renderer can change `prefs.externalPlayerPath` and torrent download roots, then invoke the existing external-player and trash capabilities. A renderer-selected nonexistent executable path reached the stubbed spawn function; a renderer-added root allowed an unrelated audit path through the trash guard.

   This requires code execution in the main UI renderer, such as an XSS or renderer compromise; this audit did not find a remote XSS entry point. It nevertheless means the sandbox does not meaningfully contain such a compromise. Sender checks alone do not solve it.

   Fix: retain sensitive permissions and actual torrent paths in the main/engine processes; accept narrow validated state updates rather than replacing the whole authorization source. Grant executable/file access through native user selection, not renderer-written preferences.

   Sources: [ipc.js:89](src/main/ipc.js#L89), [index.js:82](src/main/index.js#L82), [ipc.js:322](src/main/ipc.js#L322).

3. **High — File export and torrent creation lack a user-selection permission boundary. Reproduced using audit files.**

   `copyTorrentFile` validates its source directory but accepts any nonempty destination. The renderer copied an audit metadata file outside Downloads without opening a Save dialog. `torrent.create` also accepted and seeded a harmless file outside the test download directory without an OS file-selection grant. These are separate paths around the restrictions in finding 2.

   Impact under renderer compromise: overwrite files with available torrent metadata, or read/share files accessible to the app by creating torrents. No personal files were accessed in the reproduction.

   Fix: perform export inside the main process after a native Save dialog; use validated handles or grants for selected source files; validate engine commands and paths before seeding or writing.

   Sources: [renderer-files.js:51](src/main/renderer-files.js#L51), [preload.js](src/main/preload.js), [webtorrent.js:175](src/renderer/webtorrent.js#L175).

4. **High — Download-path containment is too broad and does not resolve symlinks. Reproduced without deleting anything.**

   The guard authorizes an entire torrent download directory, including the root itself, rather than the specific torrent files. A torrent in Downloads therefore authorizes unrelated Downloads content. A test `downloads/link/audit.txt` resolving outside Downloads also passed the guard because it only compares path strings.

   Fix: derive exact allowed targets from authoritative torrent metadata, resolve real paths where appropriate, handle symlinks explicitly, and reject deletion of broad download roots. Add tests for unrelated siblings, symlink escapes, and changing links.

   Source: [data-path.js:20](src/main/data-path.js#L20).

5. **Medium — Both SRT and VTT subtitle imports fail. Reproduced in the installed app.**

   Both fixtures fail with `TypeError: stream is not async iterable`. The old `srt-to-vtt` transform is passed directly to modern `stream/consumers.buffer`, which expects an async-iterable/web stream. VTT is also unnecessarily sent through an SRT converter.

   Fix: pass VTT through unchanged, adapt/collect SRT conversion correctly, and test real SRT/VTT files through the installed app. Bound subtitle input sizes.

   Source: [subtitles.js:23](src/main/subtitles.js#L23).

6. **Medium — Download completion throws after displaying the notification. Reproduced at the controller boundary.**

   `showDoneNotification` reads `this.state.playing`, but is called as an ordinary function, without the controller as `this`. Calling `torrentDone` with positive received bytes reproduced `Cannot read properties of undefined (reading 'playing')`. This interrupts subsequent completion handling; existing-data verification avoids that branch.

   Fix: pass the needed playing state explicitly or move the method onto the controller. Test the positive-bytes completion path, including dock updates.

   Source: [torrent-controller.js:173](src/renderer/controllers/torrent-controller.js#L173).

7. **Medium — Filtering padding files corrupts file indexes. Reproduced with a two-entry fixture.**

   The file table filters padding files before assigning indexes. With padding at original index 0 and a movie at index 1, the movie row receives index 0. Play, selection, progress and open actions then refer to the wrong torrent entry.

   Fix: attach original indexes before filtering and sorting; test an interleaved padding/media torrent.

   Source: [torrent-list-page.js:285](src/renderer/pages/torrent-list-page.js#L285).

8. **Medium — “Install VLC” fails in the sandboxed preload. Reproduced in the installed app.**

   The preload calls `shell.openExternal`, but `shell` is unavailable in this sandbox. The call throws `Cannot read properties of undefined (reading 'openExternal')`. The release-page bridge contains the same defect, although automatic update UI is no longer normally reached.

   Fix: expose main-process actions for fixed, allowlisted URLs. Keep arbitrary URL opening unavailable to the renderer.

   Source: [preload.js:56](src/main/preload.js#L56).

9. **Medium — Core UI controls are not keyboard operable and several have no accessible name. Reproduced through DOM/accessibility inspection.**

   Back, Forward, Add, player controls and torrent-row actions are clickable `<i>` elements with `tabIndex = -1` and no native keyboard activation. Several lack button roles altogether. Torrent checkboxes have empty labels. Settings path fields and the tracker textarea lack associated labels; multiple buttons are named only “Change”. The accessibility tree names the Add control “add”, not “Add torrent”.

   Fix: native `<button>` controls, properly labelled checkboxes/fields, and contextual button names. Verify Tab, Enter and Space on actual controls. Native menu shortcuts are useful but do not make these UI controls accessible.

   Sources: [header.js](src/renderer/components/header.js), [torrent-list-page.js](src/renderer/pages/torrent-list-page.js), [player-page.js:627](src/renderer/pages/player-page.js#L627), [path-selector.js](src/renderer/components/path-selector.js).

10. **Medium — Modal dialogs do not contain focus or announce themselves as dialogs. Reproduced.**

    The link modal has no dialog role or modal semantics; background controls remain in the accessibility tree. Pressing Tab after OK moved focus to a background torrent checkbox. Destructive confirmation dialogs use the same wrapper, and the shared component autofocuses the action button.

    Fix: a native dialog or complete dialog semantics, background inertness, focus containment/restoration, and safe initial focus for destructive actions. Test keyboard-only and VoiceOver flows.

    Sources: [app.js:89](src/renderer/pages/app.js#L89), [modal-ok-cancel.js](src/renderer/components/modal-ok-cancel.js). Screenshot: [link dialog](/tmp/webtorrent-audit/link-dialog.png).

11. **Medium — Player teardown never runs its intended cleanup. Reproduced.**

    The method is named `onComponentWillUnmount`, which React does not call. After leaving the local video player, `navigator.mediaSession.metadata.title` remained `monitor-test.mp4`. The intended explicit media unloading and metadata clearing are skipped. This is separate from the permanently listening server in finding 1.

    Fix: use the correct lifecycle method and clear media-session action handlers as well as metadata. Assert cleanup after switching files and returning to the list.

    Source: [player-page.js:33](src/renderer/pages/player-page.js#L33).

12. **Medium — Creating a torrent from a directory follows links outside the selected tree. Reproduced.**

    `inspectCreateInput` uses `stat` and recurses into directory symlinks. A selected test folder containing a link to a separate folder included that separate folder's file. There is no cycle detection, depth bound or concurrency bound. This can unexpectedly include material outside the folder the user intended to share and create excessive filesystem work.

    Fix: reject or explicitly handle symlinks, preserve the selection boundary, and bound traversal. Add a selected-directory-with-symlink test.

    Source: [renderer-files.js:33](src/main/renderer-files.js#L33).

13. **Medium — The test suite is currently red, and important failures are not release gates. Confirmed.**

    The two failures are `create-torrent-advanced` screenshot comparison and the created torrent's tracker list. Both still expect the old default trackers removed in the preceding task. I should have updated these expectations alongside that change. They are stale tests, not a reason to restore the trackers.

    The suite also logged two media `AbortError` renderer errors without failing on them. `test-paste-privacy.js` is not wired into the normal integration entry point or CI. `test-select-poster.js` is excluded and still uses the old WebTorrent constructor/loading and poster API. Missing screenshot baselines are silently written rather than rejected, weakening CI checks. Windows packaging exists, but the runtime test matrix does not include Windows; Linux only receives build/lint checks.

    Fix: update intentional expectations after review, make unexpected renderer failures fatal, include focused regressions in CI, and separate baseline generation from verification.

    Sources: [test/index.js](test/index.js), [test/setup.js](test/setup.js), [test/test-add-torrent.js:47](test/test-add-torrent.js#L47), [.github/workflows/ci.yml](.github/workflows/ci.yml).

**Dependency and runtime maintenance**

The live audit reported **16 affected package entries across the full tree: 15 high and 1 moderate**. The production-only report contains **11 high entries**. These counts include vulnerable transitive packages and their dependents; they are not 11 independently demonstrated exploits. There are 18 distinct advisory URLs represented in the production report. All 11 affected package entries were verified present in the installed ASAR.

| Shipped dependency group | Evidence and triage |
|---|---|
| `@xmldom/xmldom@0.9.10` | Multiple XML parsing/serialization and resource-consumption advisories. A patched compatible version is available according to npm. Trace which plist/XML inputs are remotely influenced before assigning exploit severity. |
| `ip@1.1.9` and `ip@2.0.1` | `isPublic` misclassification advisory propagates through node-ssdp, Chromecast/DLNA, tracker, discovery and WebTorrent entries. Inspected local call sites use address/packet helpers, not `isPublic`; direct exploitability in this app is not established. |

**Do not run `npm audit fix --force` blindly.** Suggested “fixes” include downgrading WebTorrent to 0.7.3 and DLNA casting to 0.0.3. Those are not acceptable modernization fixes. Update compatible transitive packages and replace or patch abandoned chains deliberately.

Electron is pinned to 43.2.0; the registry and official release page identify 44.4.3 as current stable, including upstream Chromium/PDFium/Skia/V8 fixes. WebTorrent is locked to 3.0.16 while the compatible wanted version is 3.0.21. Other available updates are recorded in the outdated report. Newer does not automatically mean vulnerable/fixed; review release notes and test upgrades.

Sources: [Electron 44.4.3 release](https://releases.electronjs.org/release/v44.4.3), [ip advisory](https://github.com/advisories/GHSA-2p57-rm9w-gvfp), and advisory links in the saved npm reports.

**Further code-reviewed risks and operational limitations**

- The hidden torrent renderer has Node integration enabled, context isolation disabled, no CSP, and no explicit navigation/window-open restrictions. It processes untrusted torrent/media data. No direct remote execution was demonstrated, but compromise there has much greater impact than in the sandboxed main UI. Move engine work to a utility process where practical and restrict the remaining media-rendering surface. [Window configuration](src/main/windows/webtorrent.js); [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security).
- Image/cover extraction reads entire torrent files into memory via `arrayBuffer`; video poster generation has no clear error/timeout cleanup path. Large or malformed inputs need explicit resource limits. No multi-gigabyte stress test was run. [Poster extraction](src/renderer/lib/torrent-poster.js).
- Configuration parsing has no recovery path for malformed JSON; load rejection is rethrown during startup. Persist failures are console-only, and shutdown eventually quits after four seconds. Users can lose recent state without a useful recovery message. This was source-reviewed, not tested against the normal user profile. [State loader](src/main/state.js), [persistence](src/renderer/lib/state.js), [startup/shutdown](src/main/index.js).
- Trash is fire-and-forget, and torrent state/metadata are removed before the native operation succeeds. A permission/volume failure can leave data behind while the torrent disappears from the list. Native rejection paths need explicit acknowledgement and UI error handling. [shell.js](src/main/shell.js), [deletion flow](src/renderer/controllers/torrent-list-controller.js).
- The local bundle is 338 MB. Its executable carries an ad-hoc signature with no Developer ID and no sealed resources, consistent with the intentionally unsigned build. It should not be distributed as a signed/notarized release. Fork links and version metadata still identify upstream WebTorrent/0.24.0, making support and build provenance ambiguous. Automatic updates remain intentionally disabled.
- A post-playback snapshot summed approximately 775.5 MiB of process working sets. Shared pages may be counted more than once; this is not unique physical memory or evidence of a leak. No long-running, many-torrent, low-disk-space, suspend/resume, or network-interruption benchmark was performed.
- Static image inspection showed readable main layouts at the tested size. The defects established here are interaction/accessibility issues, not a claim that every screen is visually broken. Preferences scroll and truncate long paths. Full VoiceOver, high-contrast, zoom, and small-screen testing remains outstanding.

**What is working**

The main UI is sandboxed, context-isolated, and has a restrictive CSP. Sender validation exists for invoke handlers and the event relay, and main-window navigation/popups are restricted. The installed app passed paste and privacy regressions; default extra trackers are empty. Video/audio/fullscreen and most torrent-list/create flows passed the existing suite. Build tools such as Playwright, esbuild and Standard were absent from the shipped ASAR. No tested audit probe touched the normal user's torrent files.

**Recommended repair order**

1. Restrict/authenticate the HTTP server and stop exposing all active torrents.
2. Repair renderer/state/file authority, including executable selection, export, seeding and symlink handling.
3. Upgrade the runtime and compatible vulnerable dependencies with targeted regression checks.
4. Fix subtitles, completion callbacks, padded-file indexing, VLC links and player cleanup.
5. Make controls and dialogs keyboard/screen-reader accessible.
6. Repair and expand CI gates, then repeat the installed-app audit before publishing.

This is a broad macOS source/runtime audit, not a proof that every defect has been found. Real Chromecast/AirPlay/DLNA devices, private-tracker interoperability, Windows/Linux execution, torrent-protocol fuzzing, native dependency internals and remote-machine firewall behavior were not validated. Each finding above distinguishes reproduction from source-based risk so those limits do not get mistaken for passing checks.
